# ADR-0005 — 在 Selkies 边界释放已按住的浏览器输入

[English](0005-release-held-input-at-selkies.md) · 简体中文

**已接受**

关联：[ADR-0002](0002-shared-selkies-chromium.zh-CN.md)、[#4](https://github.com/sagehou/dsh-workstation/issues/4)、[M0 Provider 验证](../roadmap/M0-provider-evidence.zh-CN.md)

## 背景

一名操作者与 Agent 共用一个 Chromium 进程（[ADR-0002](0002-shared-selkies-chromium.zh-CN.md)）。按 [ADR-0004](0004-single-user-release-and-deferred-sidebar.zh-CN.md)，Agent 的浏览器控制要等独占交接通过 #4 之后才能开放。

M0 已经把难点钉住。Selkies 对**新提交**的输入拦截是正确的：Agent 持有租约期间，通过 WebSocket 发送的键盘与鼠标帧不会到达渲染端，而视频在同一连接上继续。门槛 C 只在一种情况下失败，记录的断言是确切的：

```text
AssertionError [ERR_ASSERTION]: Gate C BLOCKED: a mouse button held before grant was not released by the live Selkies token update
```

HUMAN 持权时按下的鼠标键，在权限移交给 Agent 后仍然按着——因为**浏览器随后发出的释放帧被门禁连同其他输入帧一起丢弃了**。直到控制权回到 HUMAN 它才到达。于是整个 Agent 租约期间，桌面一直停留在一次拖拽中间，而这次拖拽并不是 Agent 发起的。

这不是界面问题。前端开关修不了：卡住的状态位于服务端的桌面输入后端，而能发出释放帧的客户端已经失去了发送任何内容的权限。

## 已固定的上游实际行为

以下结论对照的是确切固定的 Selkies `2.2.1`（`d6b9351421bd503ffa89bdee78e2bce758b1ffe5`），不是凭记忆：

| 事实 | 依据 |
| --- | --- |
| 权限以 `MK_ACCESS,1` / `MK_ACCESS,0` 通告。 | `websockets_mode.py:5312`（握手）、`:8356`（reconcile） |
| 仅 mk-control 变化导致的权限收回**不会**关闭连接；只有令牌吊销或角色变更才关闭。 | `reconcile_clients()` 位于 `:8298`；`should_disconnect` 仅在 `not new_perms` 或 `old_role != new_role` 时置位 |
| 释放已按住输入的既有原语存在且正确。 | `:3103` 的 `_release_held_input()` 调用 `release_mouse_buttons()` 与 `reset_keyboard()` |
| 它只在两条路径被调用：连接拆除与重连宽限期到期。权限被收回但连接仍在时，两者都不会执行。 | `:6303`、`:6382` |
| 上游 docstring 明确说明释放是有意绑定在**离开**的权限上，而非权限丢失上。 | `ws_handler()` docstring，`:5172` |
| 没有任何设置能暴露「权限丢失即释放」；`enable_collab` 与令牌表的 role/slot 是仅有的开关。 | `settings.py`、`sessions._mk_access_verdict()` 位于 `:88` |

可见上游行为本身是自洽的：它假定失去 mk-control 意味着客户端**正在离开**，因此把释放绑定在离开上。它留下的缺口恰恰就是 M0 实测的那种情况——连接仍然存活而权限被移除。

## 决策

**不 fork、不修改 Selkies。** 在输入边界上增加一个小的维护层 `browser-input-gate`，重建缺失的状态转移。

### 这一切依赖的顺序

释放**不能**在权限收回之后发出。权限在每个输入帧上按实时令牌表判定（`websockets_mode.py:6235`），而 `provision_tokens()` **先**安装新表、**再**由 `reconcile_clients()` 推送 `MK_ACCESS,0`（`:8071-8072`、`:8356`）。因此客户端得知失去权限的那一刻，能释放已按住输入的帧已经在被丢弃——这正是 M0 的失败现象，只是从服务端视角重述。

所以释放必须发生在**连接仍持有权限时**，而顺序由切换令牌表的一方负责。

1. **对 Selkies 而言，门禁就是那个 WebSocket 对端。** 操作者的浏览器连到它，它再连到 Selkies。它是真正的服务端边界，页面脚本无法绕过它直接发送帧。

2. **它用上游自己的两个原语释放，而不是靠记录按键。** 释放是 `kr` 加 `m,0,0,0,0,<seq>`。`kr` 派发 `reset_keyboard()`，释放**所有**已按住的键并纠正卡住的修饰键（`input_handler.py:9252-9256`）；零位移的相对指针消息配空按键掩码，走的正是 `release_mouse_buttons()` 的路径，而后者本身就是 `send_x11_mouse(0, 0, 0, 0, relative=True)`（`:5885-5888`）。上游的释放就是这两次调用，因此这里是复现而不是近似——它也覆盖门禁从未见过的键，那是门禁侧状态集合做不到的。

3. **门禁在返回前证明释放已被应用。** 数据连接的读循环是单一的 `async for msg in websocket`（`websockets_mode.py:5420`），会 **await** 每个输入消息的派发（`:6248`），且内联地回答 PING（`:5421-5423`，因 `autoping=False`）。因此先发两帧释放、再发一个 PING，收到 PONG 即证明它们已被派发：同一条连接、FIFO、处理器已 await。门禁以此为完成屏障，并设有超时。

   指针回显**不能**用作屏障，这一点值得记录，因为它看起来可以：当指针已经画在新位置时回显会被抑制（`input_handler.py:2013-2016`），而零位移释放恰好让指针停在原处——所以回显恰恰在这个屏障最需要的「拖拽中」场景里是静默的。

   屏障证明的是**这条连接上的派发**，而不是权限。这个区别是关键的：在已经失去权限的连接上，释放帧会在 `:6235` 被丢弃，而紧随其后的 PING 仍会被内联回应，因此在那里交接会「确认」一次从未发生的释放。门禁因此要求该连接当前持有权限，或者可证明从未持有过：门禁没有转发过任何输入的连接，不可能留下按住状态。

   无法证明的释放会被记为「未证明」，而不是当作已完成。桌面按住状态是全局的，因此页面重连本身并不能说明上次未能清除的按下已经消失；该拒绝会一直有效，直到某次交接真正证明了释放。实践中页面会自行重连，Selkies 从不变的令牌表重新授权，那次交接即完成证明。

4. **它在同一瞬间关闭操作者输入，而不是等 `MK_ACCESS,0` 到达。** 在释放与切表之间，上游仍接受操作者的帧。若此时有新的按下，它会被切表留下而卡住。因此门禁一旦开始释放就停止转发操作者输入，这段区间内不含任何客户端帧；`MK_ACCESS,0` 之后到达只是确认，而不是触发。

5. **`MK_ACCESS,1` 重新开放输入。** 交还控制是反向转移，无需释放：门禁一直关闭着输入，Agent 停止时并无按住状态。它只在明确的 resume 之后开放，因此释放尚未完成时到达的授权会被拒绝。

   如果释放屏障超时，门禁不会失败开放，也不会报告成功。它会在**该连接仍持有权限时**关闭操作者的上游连接，使 Selkies 走离开路径执行自己的 `_release_held_input()`（`:6303`），并把这次交接报告为拒绝，Provider 因而不发放租约。那次离开路径释放是预期的但未经证明，这正是拒绝会在连接消失后仍然有效的原因。

6. **它原样转发操作者的握手。** 判定这条 socket 的是 Selkies 自己：它从 `selkies.token.<base64url>` 子协议里取会话令牌，并把 `Origin` 与它收到的 `Host` 比对（`stream_server.py:2408-2442`）。门禁原样透传 `Host`、`Origin` 与子协议，因此它从不是权限来源；改写其中任何一项都会让 Selkies 拒绝操作者自己的页面。

### 控制面

状态转移的所有者必须先调用门禁，再动令牌表：

| 调用 | 含义 |
| --- | --- |
| `POST /handover` | 关闭操作者输入、释放已按住输入、等待屏障。返回 `200` 才表示已按住的输入被证明释放。其他任何响应都表示不得切表。 |
| `POST /resume` | 重新开放操作者输入。 |

Provider 的 `input(true)` 变成 **先** `POST /handover` **再** 下发收回权限的令牌表；`input(false)` 是先恢复令牌表**再** `POST /resume`。若 `/handover` 失败，Provider 让授权失败并保持租约未发放——此前只切表的做法，正是让桌面停在拖拽中间的原因。

## 为何不选其他方案

| 方案 | 否决理由 |
| --- | --- |
| 交接前用界面开关禁用输入 | 要求是在 Selkies 输入边界强制执行。开关只是建议性的：浏览器仍能发送帧，另一个标签页或构造的客户端可以完全绕过。 |
| 每次交接都关闭并重开连接 | 它确实会顺带释放按住输入，但也会中断视频、强制重新握手，并让操作者在每次转移时看到一次重连。而且 Agent 的租约将以黑屏开始。 |
| 修改 Selkies，在 `reconcile_clients()` 中调用 `_release_held_input()` | 这是最干净的修法，也应该属于上游。按 AGENTS.md 与 #4 自身的约束，产品不得 fork 核心；这保留为上游贡献候选。注意它本身也不足够：`reconcile_clients()` 在令牌表安装**之后**才运行，因此在那里释放属于「收回后释放」，正是行不通的顺序。真正能让本门禁退役的上游修法是**在安装令牌表之前**释放。此处记录为后续项，而非默默依赖。 |
| 依赖重连宽限期完成释放 | 宽限期是**离开**路径，需要连接已经消失。权限收回按设计保留连接，因此宽限期根本不会启动。 |

## 影响

- 在门禁通过完整的状态转移矩阵之前，Agent 浏览器控制保持关闭：HUMAN→AGENT、AGENT→HUMAN、租约过期、客户端断开、Chromium 重启、交接过程中的并发输入，以及 Provider 异常退出。
- 门禁成为必须构建、测试并部署的组件，且位于操作者的视频路径上。它的失败模式必须是上述的关闭型。
- 由于它是 WebSocket 对端，其正确性无需真人即可测试：通过真实连接注入帧，断言到达渲染端的内容——与 M0 实验完全相同的方式。
- 若上游「权限丢失即释放」落地，门禁的大部分逻辑可以删除，退化为薄透传。其测试在任何情况下都仍然有用。

## 尚未验证

- 门禁现已在真实栈上运行：在操作者真实的 Selkies 连接上按住不放、再交接，由 Agent 的标签页读回「一次按下、一次释放」。去掉交接调用后，同一探针会报告「有按下、无释放」，因此这项检查不是构造上必然通过。其周边的失败模式矩阵仍由假上游覆盖，而非实测。
- PING/PONG 屏障是由固定源码推论的，未实测。该论证依赖读循环在读取下一帧前 await 每个输入派发；若上游改变这一点，屏障会减弱，必须重新审视而非默认成立。
- 真实主机上的完整状态转移矩阵（HUMAN→AGENT、AGENT→HUMAN、租约过期、客户端断开、Chromium 重启、交接中的并发输入、Provider 异常退出）尚未运行。它是门禁的验收测试，不是后续事项。
- 范围内只有键盘与鼠标；文件传输、剪贴板、手柄、麦克风与摄像头在 Compose 中已禁用。输入法提交与滚动（`co`、`cmd`、`sf`、`sfe`）同样受权限门禁约束，但 `kr` 与指针掩码并不释放它们，因此在输入关闭期间被丢弃。
- 在另一显示器上仍是合法 controller 的客户端，会不会因权限丢失而被误释放，尚未考察；本部署只使用一个显示器。
