# M0 — Architecture Validation

English · [简体中文](M0.zh-CN.md)

M0 is a blocking validation milestone. Do not implement the full UI, Auth product, or production Compose until the gates below are supported by reproducible evidence.

See the [M0 evidence and decision](M0-evidence.md) for remote runs and remaining blockers.

## Gate A — DSH runtime and plugin persistence

1. Select an exact official DSH npm version from upstream metadata; do not assume prior conversation versions are current.
2. Inspect the exact DSH package engine requirements, CLI commands, Profile paths, Plugin Manager APIs, and startup behavior.
3. Build a disposable prototype runtime image with Node/pnpm/toolchain; DSH package must be installed at runtime into a persistent volume, not baked into the image.
4. Create a Web Profile using official CLI.
5. Install a known safe test plugin/Bundle from npm and a pinned Git commit if supported.
6. Verify Profile package.json, lockfile, Bundle manifest, node_modules links and pnpm store locations.
7. Recreate the container and verify plugin activation without reinstalling.
8. Install a second exact DSH version in a separate directory; switch and verify; switch back.
9. Test whether profile dependencies remain compatible. Document migration behavior and rollback constraints.
10. Test a representative native dependency build under non-root UID.

Acceptance:
- Official DSH package runs from persistent runtime path.
- At least two exact DSH versions coexist.
- Switching does not rebuild the image or overwrite versions.
- Plugin installation survives container recreation.
- pnpm store and lockfile remain intact.
- Runtime manager never mutates active version in place.
- Unsupported plugin/system dependencies are documented, not hidden.

## Gate B — LinuxServer Chromium / Selkies / CDP

1. Inspect current official LinuxServer Chromium docs and exact image startup scripts.
2. Pin a real published image tag/digest after inspecting registry metadata; do not invent a tag.
3. Launch one Chromium container with persistent /config and Selkies.
4. Verify the actual process command line includes CDP flags and a dedicated persistent user-data-dir.
5. Verify CDP /json/version and /json/list from a peer container on a private Docker network.
6. Verify CDP is not published on host/public interfaces.
7. Open a page manually in Selkies; attach Playwright over CDP to the existing default context.
8. Verify agent-opened pages appear in Selkies and human-created pages appear in CDP target enumeration.
9. Verify cookies from a test origin are shared between human and agent.
10. Restart Chromium and verify profile persistence.
11. Verify Selkies works behind Traefik at same-origin /browser/ with path prefix preserved, WebSocket functional, and iframe CSP permits only the DSH origin.

Acceptance:
- One browser process/profile is proven shared, not two synchronized browsers.
- Human and Agent see the same tabs and authenticated browser state.
- CDP is private.
- Selkies path routing and iframe work under the exact pinned image.
- Any unsupported browser operation or Playwright CDP limitation is documented.

## Gate C — Exclusive input control feasibility

This is a hard blocker for claiming Exclusive mode.

1. Determine how the pinned Selkies version injects keyboard/mouse events.
2. Determine whether human input can be disabled while preserving video observation.
3. Implement a disposable experiment to gate Selkies input when Agent lease is active.
4. Verify Agent CDP commands are rejected unless it owns a valid lease.
5. Verify lease expiry, takeover, browser disconnect, DSH restart, and concurrent requests.
6. Verify stale lease generations cannot continue issuing commands.

Acceptance:
- Agent lease prevents all human input at the actual input boundary, not just by hiding controls.
- Human lease prevents Agent tool operations server-side.
- Takeover blocks new actions, safely drains/cancels in-flight action, then enables human input.
- Failure defaults to a safe state.
- If upstream Selkies cannot be gated without maintaining a custom browser image/proxy, report the tradeoff and request a decision before proceeding.

## Gate D — DSH extension API feasibility

1. Inspect the exact selected DSH release source/docs for right sidebar tab registration, floating/docking, keep-mounted behavior, plugin lifecycle, and Browser Use provider extension points.
2. Build a minimal plugin spike that registers a tab and embeds a same-origin test iframe.
3. Verify float/dock/resize/maximize and iframe lifecycle.
4. Verify Browser Use can be wrapped/intercepted through supported extension points without DSH core fork.
5. If a supported tool interception hook is unavailable, document a standalone provider alternative.

Acceptance:
- No DSH core fork.
- Supported public extension APIs used.
- Iframe survives tab switching/float lifecycle as required.
- Browser tool calls can be gated before CDP execution.

## M0 deliverables

- Reproducible prototype Compose files.
- Exact upstream versions and image digests.
- Command logs / test evidence.
- DSH Profile and plugin persistence map.
- Selkies/CDP shared-context test report.
- Exclusive input-gating feasibility report.
- DSH plugin API feasibility report.
- Updated ADRs for any changed assumptions.
- Go/no-go decision for M1–M3.
