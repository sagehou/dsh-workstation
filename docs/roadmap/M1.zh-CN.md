## 事务化升级与恢复（#8）

`dsh-runtime upgrade` 用一个事务取代手工的 `install` + `select`。它在活动版本旁边安装候选版本，运行兼容门禁，并在 DSH_HOME 副本上执行就绪检查，记录 Profile 状态指纹，写入归档与清单，最后才移动选择指针。

| 检查 | 实际结果 |
| --- | --- |
| 真实安装上的门禁 | `0.2.2-rc.1` 扫描 591 个包，`0.2.2-rc.5` 扫描 598 个包；两者各有 30 个包声明生命周期脚本。它们属于上游，只做报告而不阻断，因为安装策略固定为 `--ignore-scripts`。 |
| 真实 Bundle 约束 | 随镜像发布的浏览器 Bundle 声明 `engines.dsh` 为 `0.2.2-rc.1`，peer `@deepseek-ai/dsh-mcp-client` 也是 `0.2.2-rc.1`，因此只要它已安装，rc.5 就会被阻断。这是真实限制，不是测试假象。 |
| 归档范围 | 排除 `runtime` 与 `pnpm` 后，同样 40 KB 的 Profile 归档从实测 223 MB 降到 2.2 KB；被排除的两棵树都可重新安装。 |
| 恢复拒绝 | 被篡改的归档、缺少清单、DSH 版本未安装的备份，以及以范围或带后缀版本提交的批准，都会被拒绝且不改动实际状态。 |

指针回滚与数据恢复是两个独立操作，`verify` 通过比较 Profile 清单、锁文件和 pnpm 存储中的包版本，判定需要哪一个。

### 容器级演练

`deploy/ci-upgrade.sh` 已在 GitHub 托管运行器上跑通：[运行 45123924853](https://github.com/sagehou/dsh-workstation/actions/runs/45123924853)（`upgrade` 作业；备份与审计记录以 `m1-upgrade-drill` 产物上传）。它在 12 个步骤中共输出 16 项通过的检查：

| 步骤 | 结果 |
| --- | --- |
| 门禁拒绝 | 固定 `0.2.2-rc.1` 的 Profile Bundle 阻断了 `0.2.2-rc.5`；候选版本仍被安装，指针与审计日志均未改变。 |
| 生命周期脚本 | 未批准的 `postinstall` 按包名阻断切换；只有精确的 `package@version` 批准才放行，范围和带后缀的版本都被拒绝。 |
| 升级 | `Backup id: 20261123T062615Z.58764fccc271`，并写入清单。 |
| 归档范围 | 含 Profile 数据；排除 `runtime` 与 pnpm 存储。 |
| `check` | 校验归档并报告记录的 DSH 版本，未执行恢复。 |
| `verify` | 真实的 `0.2.2-rc.1` → `0.2.2-rc.5` 切换后 Profile 状态**未改变**。 |
| 检测 | 合成的锁文件改动被报告为 MIGRATED，并给出匹配备份。 |
| 指针回滚 | 可执行文件回到 `0.2.2-rc.1`，而迁移过的数据保持原样。 |
| 恢复 | 恢复备份、清除合成迁移，并保留 pnpm 存储、已安装版本与审计日志。 |
| 拒绝 | 被篡改的归档和不存在的备份 id 都被拒绝。 |
| 重建 | 恢复后的 DSH_HOME 在同一镜像的新容器中再次提供服务。 |
| 镜像回滚 | 切换前捕获的镜像配合恢复的数据与选择状态再次提供服务。 |
| 审计 | 记录了 `start`、`switched`、`verified`、`pointer-rollback`、`restored`、`script-approved`，无凭据类字段。 |

### 尚未验证

- 没有已知会迁移 Profile 或插件数据的 DSH 版本；真实演练的切换报告为 `unchanged`。迁移检测与恢复由合成的锁文件改动证明，因此 DSH 自身的迁移行为在有此类版本前仍未验证。
- 门禁只报告上游生命周期脚本，无法证明运行时不需要其中任何一个；真正的防线是就绪检查。
- 演练使用 preview 组合，未启用浏览器 Bundle。已安装该 Bundle 的部署会因其 `engines.dsh` 固定而被阻断，直到匹配的 Bundle 发布。
