## 事务化升级与恢复（#8）

`dsh-runtime upgrade` 用一个事务取代手工的 `install` + `select`。它在活动版本旁边安装候选版本，运行兼容门禁，并在 DSH_HOME 副本上执行就绪检查，记录 Profile 状态指纹，写入归档与清单，最后才移动选择指针。

| 检查 | 实际结果 |
| --- | --- |
| 真实安装上的门禁 | `0.2.2-rc.1` 扫描 591 个包，`0.2.2-rc.5` 扫描 598 个包；两者各有 30 个包声明生命周期脚本。它们属于上游，只做报告而不阻断，因为安装策略固定为 `--ignore-scripts`。 |
| 真实 Bundle 约束 | 随镜像发布的浏览器 Bundle 声明 `engines.dsh` 为 `0.2.2-rc.1`，peer `@deepseek-ai/dsh-mcp-client` 也是 `0.2.2-rc.1`，因此只要它已安装，rc.5 就会被阻断。这是真实限制，不是测试假象。 |
| 归档范围 | 排除 `runtime` 与 `pnpm` 后，同样 40 KB 的 Profile 归档从实测 223 MB 降到 2.2 KB；被排除的两棵树都可重新安装。 |
| 恢复拒绝 | 被篡改的归档、缺少清单、DSH 版本未安装的备份，以及以范围或带后缀版本提交的批准，都会被拒绝且不改动实际状态。 |

指针回滚与数据恢复是两个独立操作，`verify` 通过比较 Profile 清单、锁文件和 pnpm 存储中的包版本，判定需要哪一个。

### 尚未验证

- 没有已知会迁移 Profile 或插件数据的 DSH 版本；真实演练的切换报告为 `unchanged`。迁移检测与恢复由合成的锁文件改动证明，因此 DSH 自身的迁移行为在有此类版本前仍未验证。
- 门禁只报告上游生命周期脚本，无法证明运行时不需要其中任何一个；真正的防线是就绪检查。

## 可配置子网与重叠预检（#9）

两个 Compose 子网及其中的所有地址原本是常量。现在 `deploy/network.sh` 是唯一来源：从 `WORKSTATION_SUBNET` 与 `BROWSER_SUBNET` 推导子网定义、动态 `ip_range`、每个固定地址、Provider 的绑定地址、健康检查目标与 Runtime 证书 SAN。默认值复现原有地址，因此已有部署不会换地址。

| 检查 | 观测结果 |
| --- | --- |
| 默认值保留 | 两个 Compose 文件中的 22 处 `${VAR:-default}` 均等于派生值；不一致会让「什么都不设」的升级悄悄改变地址。 |
| 自定义方案 | 在 `10.71.241.0/24` + `10.71.233.0/24` 下完整运行：`Runtime 10.71.241.2, Provider 10.71.241.3/10.71.233.2`，浏览器、Auth、备份恢复与 MCP 租约检查全部通过。 |
| 拒绝场景 | 带主机位的 CIDR、超出 `/16`..`/28` 的前缀、非 CIDR 字符串、工作区与浏览器子网重叠、覆盖 CI 代理网络的方案，全部在创建任何资源前被拒绝。 |
| 冲突诊断 | 宿主机路由与现有 Docker 网络各自都会使预检失败，指出冲突的 CIDR，并声明两个网络均未创建或改动。默认路由被有意排除。 |
| 重复初始化 | 在已有状态目录上重跑，内部 CA、Runtime 证书与所有共享密钥逐字节保留；只重写派生键。 |
| 子网变更 | 不带 `--reissue` 时拒绝；带上则为新地址替换 CA 与证书，其余密钥保留。 |

三个缺陷只有在 CI 运行真实栈时才暴露：

1. YAML flow mapping 中的 `${...}`（`{ipv4_address: ${...}}`）无法解析，四条 leg 同时失败。
2. Provider 镜像从 `prototypes/m0/provider/server.mjs` 的常量绑定 `172.30.241.3`，自定义方案下以 `EADDRNOTAVAIL` 退出。
3. Auth 同样以字面地址访问 Provider 控制口。

三项均已补充回归检查，并通过重新引入缺陷确认检查会失败。

### 尚未验证

- 在已有部署上更换子网是有损迁移：必须重建容器并把 Traefik 重连到新网络。步骤已写入文档，但未在真实主机上演练。
- 预检目前只遇到 GitHub runner 的路由表，而它们本身是干净的。真实 VPN 路由表才是它存在的理由，仍未验证。
- `--reissue` 会替换内部 CA。固定了旧 CA 的服务必须重建；文档已说明，但未端到端演练。

## 浏览器输入独占与安全交接（#4）

Agent 浏览器控制此前被关闭，因为交接时按住的鼠标键会在整个 Agent 租约期间保持按下。原因不是界面缺口，而是已固定 Selkies 的顺序特性：输入权限逐帧按实时令牌表判定（`websockets_mode.py:6235`），而 `provision_tokens()` **先**安装新表、**再**通告变更（`:8071-8072`、`:8356`）。权限收回之后发出的释放帧会与其它输入帧一起被丢弃，因此只有排在切表**之前**的释放才能落地。

`browser-gate`（ADR-0005）是数据连接前面的 WebSocket 对端，由它负责这次转移。它用 Selkies 自带的 `reset_keyboard()` 与 `release_mouse_buttons()` 原语释放，排在 Provider 切表之前，并用同一条连接上的 PING/PONG 屏障证明已被派发。

| 检查 | 观测结果 |
| --- | --- |
| 原始缺陷可复现 | 在复现真实顺序的假 Selkies 上，先切表再发送页面的释放帧，按住状态仍是 `{keys:[97], buttons:1}`。若这一点不再成立该测试会失败，因此它守住的回归不会悄悄消失。 |
| 门禁先释放 | `POST /handover` 返回 `200` 后，假桌面持有 `{keys:[], buttons:0}`。 |
| 无权限期间拒绝输入 | 权限收回后页面发送的帧不再到达桌面。 |
| 释放不依赖门禁记账 | 门禁从未转发过的键同样被释放，因为释放是无条件的，而不是从记录集合回放。 |
| 释放中途的授权被拒绝 | 交接期间返回的权限不会重新开放输入，这正是 M0 记录的竞态。 |
| 交还是显式的 | 仅一个迟到的 `MK_ACCESS,1` 不会开放输入，只有经过认证的 `/resume` 才会。 |
| 无法证明的释放失败关闭 | 上游不回应 PING 时，`/handover` 返回非 `200`、`released:false`，门禁保持 `CLOSED`。 |
| 门禁不是权限来源 | 操作者的握手会原样转发 `Host`、`Origin` 与会话令牌子协议，因此仍由 Selkies 自己判定该连接。 |
| 控制面需认证 | 任何改变状态的接口都拒绝错误或畸形的 bearer。 |
| 只代理数据连接 | 非数据连接路径被拒绝而非代理。 |

屏障的选择值得记录，因为显而易见的替代方案看起来也行得通：指针回显不能用作完成屏障，因为当指针已经画在原处时回显会被抑制（`input_handler.py:2013-2016`），而零位移释放恰好让指针停在那里。它在屏障最需要的「拖拽中」场景里恰恰是静默的。

### 尚未验证

- 门禁尚未在真实 Selkies 实例上运行。顺序与 PING/PONG 屏障由固定源码推论，未实测。
- 真实主机上的完整状态转移矩阵——HUMAN→AGENT、AGENT→HUMAN、租约过期、客户端断开、Chromium 重启、交接中的并发输入、Provider 异常退出——是门禁的验收测试，尚未运行。在通过之前 Agent 浏览器控制保持关闭。
- 容器级检查只在 CI 运行；本环境既无 Docker 也无 Go。
